# 인스턴스에 SSH로 접속되지 않습니다

## 증상

SSH 클라이언트로 인스턴스에 접속하면 연결이 되지 않고 다음과 같은 오류 메시지가 표시됩니다.

```
ssh: connect to host {인스턴스IP} port 22: Connection timed out
ssh: connect to host {인스턴스IP} port 22: Connection refused
Permission denied (publickey).
Permission denied (publickey,gssapi-keyex,gssapi-with-mic).
```

이 문서의 `{인스턴스IP}`는 접속하려는 인스턴스의 플로팅 IP 또는 사설 IP입니다. 명령을 실행할 때는 실제 IP로 바꿔 입력하세요.

인스턴스를 새로 만든 뒤 처음 접속할 때, 그리고 정상적으로 접속하던 인스턴스에서 OS 보안 취약점 조치, 백신이나 서버 접근 제어 솔루션 설치, 인스턴스 타입 변경, OS 패키지 업데이트 같은 작업을 한 뒤에 발생할 수 있습니다.

오류 메시지는 원인을 좁히는 첫 단서입니다. 아래 표에서 해당하는 메시지의 원인부터 확인하세요.

| 오류 메시지 | 의미 | 확인할 원인 |
|---|---|---|
| `Connection timed out` | 패킷이 인스턴스까지 도달하지 못하거나, 도달해도 응답이 돌아오지 않음 | 원인 1, 원인 3 |
| `Connection refused` | 인스턴스까지는 도달했지만 SSH 포트가 응답하지 않음 | 원인 3, 원인 4 |
| `Permission denied (publickey)` | 접속은 됐지만 인증에 실패함 | 원인 2, 원인 3 |

## 빠른 확인

다음을 먼저 확인하세요. 이를 통해 원인을 좁힐 수 있습니다.

1. 콘솔 **Compute > Instance** 목록의 **상태** 칼럼에서 인스턴스가 실행 중인지 확인합니다. 인스턴스를 선택하면 상세 화면 제목 옆에 상태 값이 표시됩니다. `ACTIVE`가 아니라 `SHUTOFF`이면 인스턴스를 시작한 뒤 다시 접속합니다. `ERROR`이면 아래 **문의하기**로 진행합니다.
2. SSH 포트까지 패킷이 도달하는지 확인합니다. 운영체제에 따라 다음 명령으로 확인할 수 있습니다.

    Linux와 macOS는 `nc`를 사용합니다.

    ```sh
    nc -zv {인스턴스IP} 22
    ```

    Windows는 PowerShell의 `Test-NetConnection`을 사용합니다.

    ```powershell
    Test-NetConnection {인스턴스IP} -Port 22
    ```

{% hint style="info" %}
`Test-NetConnection`은 포트를 지정해도 ping을 함께 수행하므로, 보안 그룹에 ICMP 허용 규칙이 없으면 `PingSucceeded : False`와 `WARNING: Ping to {인스턴스IP} failed -- Status: TimedOut` 경고가 함께 표시됩니다. 정상적인 구성에서도 나타나는 출력이므로 `TcpTestSucceeded` 값만 보고 판단하세요. 결과만 간단히 확인하려면 `Test-NetConnection {인스턴스IP} -Port 22 -InformationLevel Quiet`을 사용합니다.
{% endhint %}

telnet이 설치되어 있다면 `telnet {인스턴스IP} 22`로도 확인할 수 있습니다.

포트가 열려 있는데도 접속되지 않으면 네트워크 연결은 정상이며 인스턴스 내부에서 막힌 것입니다.

3. 최근에 인스턴스 안에서 한 작업을 되짚어 봅니다. 실제 문의에서 가장 많은 원인은 보안 취약점 조치, 백신이나 서버 접근 제어 솔루션 설치처럼 **사용자가 OS 안에서 수행한 변경**입니다. 변경 직후부터 접속되지 않는다면 원인 3을 먼저 확인하세요.

{% hint style="info" %}
같은 프로젝트의 다른 인스턴스에는 접속되는지도 함께 확인하세요. 다른 인스턴스는 정상이고 특정 인스턴스만 접속되지 않으면 네트워크 설정보다 그 인스턴스 내부를 먼저 확인해 봐야 합니다.

다만 같은 조치를 여러 인스턴스에 한꺼번에 적용했다면 전부 접속되지 않을 수 있습니다. 실제 문의 중에는 보안 취약점 조치를 10대에 동일하게 적용한 뒤 10대 모두 접속이 막힌 사례가 있습니다. 이 경우에도 네트워크가 아니라 OS 내부가 원인입니다.
{% endhint %}

## 원인과 해결 방법

원인은 접속 경로, 인증, 인스턴스 내부의 세 단계에 걸쳐 있습니다. 다음 흐름으로 원인을 좁힌 뒤 해당 원인의 해결 방법을 적용하세요.

![SSH 접속 실패 원인 판단 흐름](images/instance-ssh-connection-failed-flow.svg)

### 원인 1: 접속 경로가 인스턴스까지 닿지 않음

`Connection timed out`은 패킷이 인스턴스까지 도달하지 못하는 경우가 대표적이지만, 패킷이 도달해도 인스턴스 안에서 DROP되면 같은 메시지가 표시됩니다. 아래 가이드대로 경로를 모두 열어도 같은 메시지가 계속되면 원인 3을 확인하세요.

인스턴스의 사설 IP는 VPC 내부에서만 통신하므로 외부에서 바로 접속할 수 없습니다.

외부에서 접속하려면 **플로팅 IP를 인스턴스에 연결하고, 그 인스턴스가 속한 서브넷의 라우팅 테이블에 인터넷 게이트웨이가 연결되어** 있어야 합니다. VPN을 사용하거나, 이미 외부 접속이 가능한 배스천 호스트를 거쳐 접속하는 방법도 있습니다.

이렇게 경로가 여러 단계이고 각 단계가 SSH 포트를 통과시켜야 하므로, 어느 한 곳만 막혀도 `Connection timed out`이 발생합니다.

SSH 포트를 22번이 아닌 다른 번호로 바꿔 운영하는 환경에서 특히 자주 발생합니다. `sshd_config`에서 포트를 바꿔도 경로 위의 규칙은 함께 바뀌지 않으므로 양쪽을 모두 맞춰야 합니다. 접속하는 쪽의 공인 IP가 유동 IP인 경우에도 어제까지 되던 접속이 갑자기 막힙니다.

**해결 방법**

바깥에서 안쪽 순서로 확인합니다. 앞 단계가 막혀 있으면 뒤 단계를 확인해도 의미가 없습니다.

1. **플로팅 IP 연결**: 인스턴스를 선택하고 하단 상세의 **네트워크** 탭에서 **플로팅 IP** 칼럼에 값이 있는지 확인합니다. 비어 있으면 외부에서 접속할 수 없습니다. 인스턴스 목록에서 **플로팅 IP 관리**를 클릭해 연결합니다.
2. **보안 그룹 수신 규칙**: 콘솔 **Network > Security Groups**에서 인스턴스에 적용된 보안 그룹을 모두 선택해 **보안 규칙** 탭에 SSH 포트를 허용하는 규칙이 있는지 확인합니다. 보안 그룹은 허용 규칙만 가지므로 여러 개 중 하나에라도 허용 규칙이 있으면 통과합니다. 없으면 **보안 규칙 생성**으로 규칙을 추가합니다. **방향**은 `수신`, **IP 프로토콜**은 `TCP`, **포트 범위**는 실제 사용하는 SSH 포트, **원격**은 접속할 IP 대역(CIDR)으로 지정합니다.

{% hint style="warning" %}
관리 포트를 `0.0.0.0/0`으로 열면 무작위 로그인 시도에 노출됩니다. 회사 공인 IP 대역이나 VPN 대역만 허용하세요. 원인을 확인하려고 일시적으로 전체 허용했다면 확인 후 반드시 되돌립니다.
{% endhint %}

3. **라우팅 테이블의 인터넷 게이트웨이 연결**: 콘솔 **Network > Routing**에서 인스턴스가 속한 VPC의 라우팅 테이블을 확인합니다. 목록의 **인터넷 게이트웨이** 칼럼이 비어 있으면 외부에서 플로팅 IP로 접속할 수 없습니다. 해당 라우팅 테이블을 선택한 뒤 **인터넷 게이트웨이 연결**을 클릭해 연결합니다.
4. **Network ACL**: 서브넷에 Network ACL을 바인딩했다면 규칙을 확인합니다. 콘솔 **Network > Network ACL**에서 해당 ACL을 선택하고 **ACL Rule** 탭을 엽니다. 규칙은 **순서**가 낮은 것부터 적용되므로, **적용 방법**이 `차단`인 규칙이 앞 순서에 있으면 뒤에 허용 규칙이 있어도 막힙니다. **목적지 포트**와 **출발지 CIDR**에서 SSH 포트를 막는 규칙이 있는지 확인합니다.

{% hint style="info" %}
Network ACL의 기본 규칙은 순서 `101`이 전체 **허용**, 순서 `32765`가 전체 **차단**입니다. 이 두 개만 있는 상태라면 모든 트래픽이 통과하므로 Network ACL은 원인이 아닙니다. Network ACL을 바인딩하지 않았다면 이 단계는 건너뜁니다.
{% endhint %}

5. **접속하는 쪽 네트워크**: 사내 방화벽이나 보안 정책에서 SSH 포트의 아웃바운드 통신이 막혀 있는지 확인합니다. 다른 네트워크(예: 모바일 테더링)에서 접속해 보면 빠르게 구분할 수 있습니다.
6. **공공 클라우드(GOV) 환경**: 공공 클라우드는 SSL VPN을 거친 접속을 기본으로 하며 VPN 대역 밖에서는 SSH 접근이 허용되지 않습니다. 아래 **공공 클라우드 환경의 접속 경로**를 참고하세요.

여기까지 모두 열려 있는데도 접속되지 않으면 네트워크가 아니라 인스턴스 내부 문제입니다. 원인 3으로 넘어가세요.

#### 공공 클라우드 환경의 접속 경로

1. SSL VPN에 로그인한 뒤 VPN 네트워크에 매핑된 플로팅 IP로 접속합니다. VPN 계정은 리전별로 신청해야 하므로 접속하려는 리전의 계정이 있는지 확인합니다. 자세한 내용은 [SSL VPN 콘솔 사용 가이드](https://docs.gov-nhncloud.com/ko/Security/SSL%20VPN/ko/console-guide/)를 참고하세요.
2. VPN에 로그인한 뒤 `ipconfig` 또는 `ifconfig`로 할당받은 클라이언트 IP를 확인하고, 그 IP를 보안 그룹의 수신 규칙에 추가합니다.
3. VPN 네트워크는 접속 전용 대역이므로 인스턴스의 첫 번째 네트워크 인터페이스(eth0)가 아니라 두 번째 인터페이스(eth1)에 연결해야 정상 통신합니다.
4. Network Firewall과 SSL VPN을 함께 사용하는 환경이면 라우팅 테이블을 확인합니다. Network Firewall용 서브넷과 그 외 리소스(웹 서버, WAF 등)의 라우팅 테이블은 분리되어야 하며, 분리된 라우팅 테이블에 게이트웨이가 `NetworkFirewall_INF_TRAFFIC_VIP`인 라우트가 필요합니다. 목적지는 `0.0.0.0/0` 또는 SSL VPN IP로 지정하며 환경에 맞게 다르게 설정할 수 있으므로, 목적지 값보다 **해당 게이트웨이로 향하는 라우트가 있는지**를 확인합니다.

{% hint style="info" %}
공공 클라우드(GOV) 환경에서는 **SSL VPN 정책이 인스턴스가 아니라 VPN 네트워크에 연결된 플로팅 IP에 적용**됩니다. 이 플로팅 IP는 Network Firewall NAT 설정 화면에서 **NAT 전 공인 IP**로 표시됩니다.
{% endhint %}


### 원인 2: 키페어가 일치하지 않거나 키 파일을 사용할 수 없음

인스턴스는 생성할 때 지정한 키페어의 공개 키를 OS 계정의 `authorized_keys`에 등록합니다. 접속할 때 제시하는 개인 키(pem 파일)가 이 공개 키와 짝이 아니면 `Permission denied (publickey)`가 발생합니다.

SSH는 다른 사용자가 읽을 수 있는 개인 키를 무시하므로, 키 파일이 맞아도 파일 권한이 넓으면 인증에 실패합니다. 접속 계정 이름이 이미지와 맞지 않을 때도 같은 메시지가 표시됩니다. 계정 이름은 Rocky Linux는 `rocky`, Ubuntu는 `ubuntu`, Debian은 `debian`입니다. 이전에 CentOS 이미지로 만든 인스턴스는 `centos`를 사용합니다.

{% hint style="info" %}
pem 파일을 분실했다면 새 키페어를 만든 뒤 인스턴스 상세 **기본 정보** 탭에서 **키페어 > 변경**으로 교체해 접속할 수 있습니다. 키페어 변경은 인스턴스가 활성 상태여야 하고 기본 인프라 서비스 ADMIN 권한이 필요하며, Windows 인스턴스와 생성에 사용한 이미지 버전이 낮은 인스턴스는 지원되지 않습니다.

**키페어를 변경하면 대상 OS 계정의 `authorized_keys`가 새 공개 키로 덮어써집니다.** 직접 등록해 둔 다른 공개 키가 있으면 함께 사라지므로, 여러 키를 등록해 운영하는 환경에서는 변경 후 기존 키로 접속이 안 되는 상황이 발생합니다. 키페어를 변경하기 전에 기존 공개 키를 백업해 두고, 변경 후 다시 추가하는 것이 필요합니다.
{% endhint %}

**해결 방법**

1. 콘솔 **Compute > Instance** 목록의 **키페어** 칼럼이나 인스턴스 상세 **기본 정보** 탭의 **키페어** 항목에서 인스턴스에 지정된 키페어 이름을 확인하고, 접속에 사용하는 pem 파일이 그 키페어의 파일인지 대조합니다. 인스턴스 상세의 **접속 정보** 탭에서 키페어 이름과 계정 이름이 반영된 접속 명령을 **복사**해서 그대로 사용할 수 있습니다.
2. pem 파일 권한을 소유자만 읽을 수 있도록 바꿉니다. `Permissions 0644 for 'your-key.pem' are too open.` 메시지가 표시되는 경우도 마찬가지입니다.

    ```sh
    chmod 600 {키페어이름}.pem
    ```

    다른 인스턴스에 pem 파일을 올려 두고 그 인스턴스에서 접속하는 구성이라면 올려 둔 파일의 권한도 함께 확인합니다.

3. 접속 계정 이름이 이미지에 맞는지 확인합니다. `-v` 옵션을 붙이면 실제로 어떤 계정과 키 파일이 사용됐는지 확인할 수 있습니다.

    ```sh
    ssh -i {키페어이름}.pem rocky@{인스턴스IP} -v
    ```

    출력의 `debug1: Authenticating to {인스턴스IP}:22 as 'rocky'`에서 접속에 사용된 계정 이름을, `debug1: Trying private key: {키페어이름}.pem`에서 실제로 제시한 키 파일을 확인합니다.

4. 키 파일과 계정 이름, 권한이 모두 맞는데 계속 `Permission denied`가 발생하면 OS 안에서 `authorized_keys`나 sshd 인증 설정이 바뀐 것입니다. 원인 3으로 넘어가세요.

### 원인 3: OS 안에서 SSH 로그인이 차단됨

실제 문의에서 가장 많은 원인입니다. SSH 서버(sshd)는 설정 파일 하나로 동작하지 않고 여러 요소가 함께 맞아야 하며, 이 중 하나만 어긋나도 로그인이 막힙니다.

- `/etc/ssh/sshd_config`: 포트, 인증 방식, 접속 허용 계정
- PAM 설정: 계정 잠금, 비밀번호 정책. 파일 경로가 OS 계열마다 다릅니다.
    - Rocky Linux, CentOS 계열: `/etc/pam.d/system-auth`, `/etc/pam.d/password-auth`
    - Ubuntu, Debian 계열: `/etc/pam.d/common-auth`, `/etc/pam.d/common-account`
- `/etc/group`의 `ssh_keys` 그룹: 호스트 키 파일 접근에 사용. Rocky Linux, CentOS 계열에만 있습니다.
- OS 방화벽(firewalld, iptables, ufw)과 SELinux
- 백신이나 서버 접근 제어 솔루션이 자체적으로 적용하는 차단 정책

보안 취약점 조치 과정에서 이 요소들을 바꾼 뒤 접속이 막히는 사례가 많이 발생합니다.

- `/etc/group`에서 `ssh_keys` 그룹 줄을 주석 처리(`#ssh_keys:x:995:`)해 sshd가 정상 동작하지 못한 경우
- 계정 잠금 임계값을 설정하려고 PAM 설정 파일에 규칙을 한 줄씩 추가한 뒤 모든 계정의 로그인이 차단된 경우
- 백신이나 서버 접근 제어 솔루션을 설치한 뒤 sshd는 정상 동작하는데도 접속이 차단된 경우

이런 문제는 **조치한 직후가 아니라 나중에 드러납니다.** 이미 연결된 세션은 그대로 유지되기 때문에, 세션을 닫고 다시 접속할 때 비로소 알게 됩니다. 조치 후 수일이 지나 발견되면 어떤 작업이 원인인지 특정하기 어려워집니다.

**해결 방법**

인스턴스 안으로 들어가야 확인할 수 있으므로, SSH가 아닌 시리얼 포트로 접속하는 시리얼 콘솔을 사용합니다. 시리얼 콘솔은 SSH를 쓸 수 없을 때를 위한 **긴급용 접속 수단**이며, 커널 단계 조치를 목적으로 제공됩니다.

{% hint style="warning" %}
시리얼 콘솔을 사용하기 위해서는 다음 조건을 확인하세요.

- **OS 계정 이름과 비밀번호를 미리 설정해 두어야 합니다.** 시리얼 콘솔은 커널 조치가 목적이라, 부팅 이후 실제 OS에 로그인하려면 키페어가 아니라 계정 비밀번호가 필요합니다. **장애가 난 뒤에는 설정할 수 없습니다.**
- **인스턴스가 시리얼 콘솔로 출력하도록 설정되어 있어야 합니다.** 아래 **문제 예방하기**를 참고하세요.
- **Windows 인스턴스는 시리얼 콘솔을 지원하지 않습니다.**
- 개인이 업로드한 이미지로 만든 인스턴스는 접속이 보장되지 않습니다.
- **2026년 1월 27일 이전에 생성한 인스턴스는 인스턴스 중지 후 인스턴스 시작이 필요합니다. 인스턴스 재부팅으로는 적용되지 않습니다.**
- **2024년 11월 26일 이전에 생성한 인스턴스는 GRUB 설정도 함께 바꿔야 합니다.** 아래 **문제 예방하기**를 참고하세요.

뒤의 두 조건은 인스턴스를 중지하거나 OS 안에서 설정을 바꿔야 하므로, **접속이 이미 불가한 상태에서는 준비할 수 없습니다.** 평상시에 미리 확인해 두어야 장애 상황에서 쓸 수 있습니다.

시리얼 콘솔을 쓸 수 없는 경우에는 **문의하기**로 이동하세요.
{% endhint %}

1. 인스턴스를 선택하고 하단 상세 **기본 정보** 탭의 **로그** 항목에서 **시리얼 콘솔 연결**을 클릭합니다. 시리얼 콘솔은 SSH가 아니라 시리얼 포트를 쓰는 경로이므로, 보안 그룹이나 sshd 상태와 상관없이 사용할 수 있습니다. 인스턴스당 하나의 연결만 가능하고 한 번에 최대 10분간 접속됩니다.
2. `login:` 프롬프트에서 OS 계정으로 로그인합니다.
3. sshd 상태와 설정 문법을 확인합니다. 설정 파일에 문법 오류가 있으면 sshd가 재시작에 실패해 아예 응답하지 않습니다.

    ```sh
    sudo systemctl status sshd
    sudo sshd -t

    # Rocky Linux, CentOS 계열
    sudo journalctl -u sshd -n 50 --no-pager

    # Ubuntu, Debian 계열
    sudo journalctl -u ssh -n 50 --no-pager
    ```

4. 최근에 수정한 파일을 원래대로 되돌립니다. 백업이 없으면 추가한 줄만 주석 처리하고, `/etc/group`의 `ssh_keys` 그룹을 주석 처리했다면 주석을 해제합니다.
5. 설정을 되돌린 뒤 sshd를 재시작하고, **시리얼 콘솔 세션을 닫지 않은 상태에서** 다른 터미널로 SSH 접속을 시도합니다. 설정이 잘못되어도 열려 있는 세션으로 다시 되돌릴 수 있습니다.

    ```sh
    sudo systemctl restart sshd
    ```

    sshd 재시작만으로 복구되지 않으면 인스턴스를 재부팅합니다.

### 원인 4: 인스턴스가 정상 부팅되지 않음

인스턴스 상태는 실행 중인데 OS가 부팅 도중 멈추면 sshd가 시작되지 않아 `Connection refused`가 발생합니다. 커널이 정상적으로 기동되지 않은 경우가 여기 해당합니다.

**해결 방법**

1. 인스턴스를 선택하고 하단 상세 **기본 정보** 탭의 **로그** 항목에서 **로그 보기**와 **스크린숏 보기**로 부팅이 어디에서 멈췄는지 확인합니다. 이 두 가지는 접속하지 않고 화면과 로그만 확인하는 기능이라, 시리얼 콘솔을 쓸 수 없는 인스턴스에서도 사용할 수 있습니다.
2. 더 자세히 확인하거나 조치가 필요하면 **시리얼 콘솔 연결**로 접속합니다.

{% hint style="info" %}
시리얼 콘솔은 접속 후 10분이 지나면 연결이 끊깁니다. 의도된 동작이므로 다시 접속하면 됩니다. 재접속 시 이전 출력이 사라진 채 입력을 기다리는 상태일 수 있으니, 화면이 비어 있으면 Enter를 먼저 입력해 보세요. 인스턴스당 하나의 연결만 가능하므로, 다른 창에서 이미 접속해 두었다면 그 창을 먼저 닫아야 합니다.
{% endhint %}

3. 커널 문제로 판단되면 재부팅 중 GRUB 메뉴에서 이전 커널을 선택해 부팅합니다. 부팅에 성공하면 문제가 없는 커널을 기본값으로 지정합니다.

{% hint style="warning" %}
시리얼 콘솔로 인스턴스에 접속하여 부팅 방법을 변경하면 부팅에 실패할 수 있으며, 이에 따른 결과에 대한 책임은 사용자에게 있습니다.

특히 복구 목적으로 커널 부팅 인자에 `init=/bin/bash`를 넣었다면 반드시 임시로만 사용하고 복구 후 제거하세요. 이 값이 영구 설정으로 남으면 systemd 대신 bash가 실행되어 부팅이 비정상 상태가 되고, 재부팅 시 커널 패닉(`Attempted to kill init`)이 발생할 수 있습니다.
{% endhint %}

4. 시리얼 콘솔에 접속했는데 검은 화면만 표시되고 아무 출력도 없다면, 인스턴스가 시리얼 콘솔로 출력하도록 설정되어 있지 않은 것입니다. 시리얼 콘솔 자체는 접속된 상태이므로 Enter를 입력해 프롬프트가 표시되는지 먼저 확인하고, 그래도 비어 있으면 아래 **문제 예방하기**의 시리얼 콘솔 설정을 참고하세요. 이 상태에서는 인스턴스 안을 볼 수 없으므로 **문의하기**로 원격 지원을 요청해야 합니다.

## 문의하기

위 방법으로 해결되지 않거나 인스턴스 안으로 들어갈 수 없으면 [NHN Cloud 고객지원](https://www.nhncloud.com/kr/support/inquiry)에 문의하세요.

SSH 접속이 불가하고 시리얼 콘솔도 사용할 수 없는 상황에서는 NHN Cloud가 인스턴스에 직접 접근해 조치하는 원격 지원이 필요합니다. 원격 지원을 요청하려면 문의 본문에 **"접근하여 조치 부탁드립니다"** 문구를 넣고 다음 정보를 함께 전달하세요.

| 항목 | 설명 |
|---|---|
| 리전 | 인스턴스가 있는 리전 |
| 프로젝트 ID | **프로젝트 관리** 탭의 프로젝트 기본 정보 영역에서 확인 |
| 인스턴스 ID | 인스턴스 선택 후 하단 상세 **기본 정보** 탭의 인스턴스 이름 아래 UUID(**복사** 버튼 제공) |
| 작업 내용 | 접속이 되지 않기 직전에 인스턴스 안에서 수행한 작업 |
| 복구 방법 | 접속 후 수행해야 할 작업과 확인할 부분을 명령어 단위로 구체적으로 기재 |
| 루트 비밀번호 | 설정해 둔 값이 있으면 전달 |
| 연락처 | 조치 진행 상황을 안내받을 연락처 |
| 작업 시간 | 재부팅이 가능한 시간대 |

{% hint style="info" %}
**복구 방법을 구체적으로 적어주세요.** 원격 지원은 NHN Cloud가 전달받은 절차를 대신 수행하는 방식이므로, 되돌려야 할 파일과 줄, 실행할 명령어를 그대로 적어 주세요. 복구 절차를 파일로 정리해 첨부해 주셔도 빠른 조치에 도움이 됩니다.
{% endhint %}

{% hint style="warning" %}
루트 비밀번호가 없으면 인스턴스를 재부팅해야 접속할 수 있습니다. 서비스 중단이 발생하므로 재부팅이 가능한 시간을 함께 전달하세요. 비밀번호를 설정한 적이 없다면 임의로 설정해 달라고 요청할 수도 있습니다.
{% endhint %}

진단 속도를 높이려면 다음 자료도 함께 전달하세요.

- 접속이 되지 않은 시각(KST 기준)
- `ssh -i {키페어이름}.pem {계정}@{인스턴스IP} -v` 실행 결과 전문
- 접속 경로를 확인한 결과: `nc -zv {인스턴스IP} 22` 또는 `Test-NetConnection {인스턴스IP} -Port 22` 출력 화면
- 같은 대역의 다른 인스턴스에서 사설 IP로 접속을 시도한 결과
- 인스턴스에 적용된 보안 그룹의 **보안 규칙** 화면
- 시리얼 콘솔 화면(검은 화면이면 그 상태 그대로)
- 인스턴스 안에서 확인 가능한 경우 로그
    - Rocky Linux, CentOS 계열: `/var/log/messages`, `journalctl -u sshd`
    - Ubuntu, Debian 계열: `/var/log/syslog`, `journalctl -u ssh`

인스턴스 내부와 네트워크 구성을 함께 확인해야 하는 경우 담당자 초대를 요청받을 수 있습니다. **멤버 관리** 탭에서 **기술 지원 담당자 추가**를 클릭해 초대하며, 조직과 프로젝트 양쪽에 초대해야 합니다.

## 문제 예방하기

SSH 접속 불가는 접속 경로가 하나뿐일 때 복구가 어려워집니다. 다음을 미리 준비해 두면 같은 상황에서 스스로 복구할 수 있습니다.

- **시리얼 콘솔을 평상시에 미리 준비**: 인스턴스 생성 시점에 따라 준비 작업이 다릅니다.

    **2026년 1월 27일 이전에 생성한 인스턴스**는 **인스턴스 중지** 후 **인스턴스 시작**을 해야 기능이 활성화됩니다. 서비스 영향이 없는 시간에 미리 처리해 두세요.

    **2024년 11월 26일 이전에 생성한 인스턴스**는 GRUB 설정도 함께 바꿔야 합니다. 설정 파일과 적용 명령이 OS 계열마다 다르므로 사용 중인 이미지에 맞게 변경합니다.

    ```
    GRUB_TIMEOUT=3
    GRUB_TERMINAL="console serial"
    GRUB_SERIAL_COMMAND="serial --speed=9600 --unit=0 --word=8 --parity=no --stop=1"
    ```

    ```sh
    # Ubuntu, Debian 계열
    sudo vi /etc/default/grub.d/50-cloudimg-settings.cfg
    sudo update-grub
    ```

    ```sh
    # Rocky Linux, CentOS 계열
    sudo vi /etc/default/grub
    sudo grub2-mkconfig -o /boot/grub2/grub.cfg
    ```

    준비를 마쳤으면 **OS 계정 이름과 비밀번호를 설정**하고, 평상시에 한 번 **기본 정보** 탭의 **시리얼 콘솔 연결**로 접속해 `login:` 프롬프트가 표시되는지 확인하세요. 시리얼 콘솔은 커널 조치를 목적으로 하는 긴급용 수단이라, 계정과 비밀번호를 미리 설정해 두지 않으면 부팅 이후 단계로 넘어갈 수 없습니다. 프롬프트가 보이지 않으면 커널 부팅 인자에 시리얼 콘솔 출력이 설정되어 있지 않은 것이므로, 다음과 같이 확인합니다.

    ```sh
    # console=ttyS0 이 있어야 시리얼로 출력됩니다
    cat /proc/cmdline
    systemctl is-enabled serial-getty@ttyS0.service
    ```

    값이 없으면 커널 부팅 인자를 추가합니다. 이 역시 OS 계열마다 명령이 다릅니다. Rocky Linux, CentOS 계열은 `grubby`를 사용합니다.

    ```sh
    sudo grubby --update-kernel=ALL --args="console=tty0 console=ttyS0,115200n8"
    sudo systemctl enable serial-getty@ttyS0.service
    ```

    Ubuntu, Debian 계열에는 `grubby`가 없으므로 `/etc/default/grub`의 `GRUB_CMDLINE_LINUX` 줄에 다음 값을 넣습니다.

    ```
    GRUB_CMDLINE_LINUX="console=tty0 console=ttyS0,115200n8"
    ```

    ```sh
    sudo vi /etc/default/grub
    sudo update-grub
    sudo systemctl enable serial-getty@ttyS0.service
    ```

    적용에는 재부팅이 필요합니다.

- **OS 보안 조치는 백업과 세션 유지를 전제로 진행**: 인스턴스 이미지나 블록 스토리지 스냅샷을 먼저 만들고, 접속 중인 세션을 닫지 않은 상태에서 다른 터미널로 접속을 확인한 뒤 세션을 닫습니다. sshd 설정을 바꿨다면 재시작 전에 `sudo sshd -t`로 문법을 검사합니다.
- **한 대에서 먼저 검증한 뒤 확대 적용**: 문제가 된 항목은 조치 직후가 아니라 세션을 닫거나 재부팅한 뒤에 드러납니다. 운영 인스턴스 여러 대에 한꺼번에 적용하지 말고, 같은 이미지로 만든 인스턴스 한 대에서 재부팅까지 확인한 뒤 확대하세요.
- **변경 내역과 복구 절차를 함께 기록**: 어떤 파일의 어떤 줄을 바꿨는지 적어 두면 자력 복구가 빨라지고, 원격 지원을 요청할 때도 그대로 전달할 수 있습니다.
